# Synchro son / image (latence, pulsation, avance)

Fiche de [CLAUDE.md](../../CLAUDE.md) (issue #132 : detail deplace tel quel). Fichiers : core/pulse.py, core/latency.py, engine/audio.py (horodatage, _lead_step), tools/mesure_latence.py, tools/calibrer_avance.py, tools/bench_kick.py.

**Latence mesuree** (`python tools/mesure_latence.py`, `check_latence` dans `check_gl.py`) : un kick est injecte, la vraie chaine (`AudioAnalyzer` + `Renderer`, strobe en mode kick) le montre ; on releve debut du son -> kick detecte -> premiere image rendue avec l'eclair (compteur `Renderer.strobe_fired` : un eclair de 70 ms peut tomber entre deux images d'un rendu logiciel lent, le pixel blanc seul le rate)
(`fbo.read`, donc rendu termine), rendu simule a 60 images/s. Mode interne (defaut, sans materiel) : kicks ecrits dans le tampon audio par blocs de 512 au rythme reel. Poste de dev, processus seul : **mediane ~29 ms, pire 44 ms** (analyse ~18 ms, rendu ~16 ms) ;
dans la suite de tests, avec les autres fils qui tournent, ~74 ms (information, non bloquant). `--materiel` joue le kick par la sortie audio et l'ecoute par l'entree reelle (ajoute tampons des cartes son et trajet acoustique ; **a lancer a la main**, il fait du bruit :
casque contre le micro ou haut-parleur pres de lui). **Reste hors mesure : l'affichage** (balayage de l'ecran, traitement du videoprojecteur) ; seule une camera rapide ou une photodiode le donne. Le chiffre est donc un minimum pour ce que voit le public.

**Synchro son / image, lot 1 (mesure ; spec `docs/plans/2026-11-12-synchro-son-image-design.md`, issues #110 et #96)** : (1) **horodatage a la capture** : `RingBuffer.write(x, t_end)` garde l'instant de fin de chaque bloc (`stamps`, `time_at`) ; `SoundDeviceInput._callback` le date par l'horloge du pilote (`capture_age` : `currentTime - inputBufferAdcTime`, 0 si absurde). `AudioAnalyzer._audio_time` rend `t_end + retard stable` (plancher glissant de 3 s, lisse 0,5 s : la gigue d'ordonnancement du fil disparait) ; `Rhythm` et `PhaseTracker` l'utilisent (BPM, grille). Les enveloppes visuelles gardent l'instant de traitement : **aucun changement visible**. (2) **retard publie** : `state["audio_age_ms"]` / `["audio_age_floor_ms"]`, `s.status["audio_age_ms"]`, titre de la fenetre de rendu (« son N ms ») et `--stats`. (3) **`tools/calibrer_avance.py`** (`emettre` / `analyser` / `liste`) : un clic de kick par le haut-parleur, la vraie chaine l'entend par le micro et fait flasher la fenetre, un telephone en ralenti (120 / 240 i/s) filme ecran + haut-parleur ; l'analyse (ffmpeg) rend la mediane du retard = « Avance » recommandee (reglage du lot 4). Limites : fenetre Tk (pas la fenetre GL), decalage audio / video du telephone, valable pour CE materiel. (4) **diagnostic** : `check_microphone` dit l'API hote et la latence annoncee (MME = avertissement ; WASAPI = penser aux « ameliorations audio »). `check_gl.py` : `check_calibration` (dans `PURES`). **Non verifie** : une vraie calibration (projecteur, micro, camera).

**Synchro son / image, lot 2 (banc du detecteur de kick ; issue #96)** : `tools/bench_kick.py` rejoue de l'audio dans le vrai `FeatureExtractor` par blocs de 512, a vitesse simulee (un morceau de 3 min en quelques secondes), et le compare a une verite terrain `<audio>.kicks.json` (`{"kicks": [s...]}` ou une liste ; `annoter <audio>` la pre-remplit avec le detecteur, **a corriger a la main** : le fichier porte `"source": "detecteur"` et le rapport le signale). Metriques : rappel, precision, F1, erreur de datation (mediane, p95 ; un kick est date a la FIN du bloc de detection), doubles, faux kicks par minute sur passage sans kick. `--sensibilites 0.7,1,2.5`, `--json` (comparable d'une version a l'autre), `--dossier <chemin>` pour les enregistrements reels (WAV direct, MP3 / FLAC par ffmpeg ; **hors depot**). Corpus synthetique a verite connue (house, techno + grondement, breakbeat, lent, kick sature, telephone, kick sur basse continue, passages sans kick). **Diagnostic de depart (sensibilite 1)** : rappel 0,97 / precision 1,0 sur les morceaux normaux, 0,87 sur kick sature, **retard median de datation ~30 ms** (cible du lot 3 : < 20 ms), kick sur basse continue manque (rappel 0,10 ; 0,97 a la sensibilite 2,5), et **un passage sans kick avec claps / caisses claires donne ~50-60 faux kicks par minute** (chaque clap compte ; une nappe ambiante : 0, mais 54 /min a la sensibilite 2,5). `check_gl.py` : `check_bench_kick` (dans `PURES`, seuils de non-regression sur le synthetique). **Non verifie** : le banc sur de vrais enregistrements de l'utilisateur.

**Synchro son / image, lot 3 (attaque rapide ; issue #110)** : la FFT de 2048 (43 ms) ne voyait un kick qu'~30 ms apres son debut. `core.onset.FastAttack` (pur) detecte l'attaque dans le **domaine temporel** : `FeatureExtractor._fast_attack` ramene les echantillons NEUFS du pas a ~1 kHz (moyenne de blocs de ~1 ms : `chunk` = signal des basses, `broad` = puissance du signal complet), le detecteur filtre (passe-bas 170 Hz), lisse l'energie (6 ms) et declare l'attaque quand elle sort de son creux des 100 ms precedentes (x4 a sensibilite 1) ET de sa moyenne lente (x2,2) ET que les basses representent au moins 15 % de la puissance totale (un clap ou un charley n'est pas un kick) ; elle n'agit qu'apres 1,5 s de signal (`SETTLE_S`, avant : FFT seule : un faux depart sur une note de basse a ete vu en banc). La detection FFT reste inchangee et **partage la periode refractaire** (`last_beat`) : un kick = une detection. `FeatureExtractor.fast_attack = False` (banc : `--sans-rapide`) rend le comportement d'avant. **Mesure (banc, sensibilite 1)** : retard median de datation 30 -> 11-20 ms (house 16, techno 20, breakbeat 11, lent 13, telephone 8), F1 inchange ; chaine logicielle de `mesure_latence.py` 29 -> **16 ms** mediane ; cout CPU de l'analyse +0,5 % d'un coeur (1,2 -> 1,7 %). Inchange : kick sature (37 ms : sa queue longue ne sort pas assez de son creux, c'est la FFT qui le voit), claps sans kick (~50-60 faux /min, comme avant), kick sur basse continue (rappel 0,49 au lieu de 0,10, la sensibilite 2,5 reste le recours). `check_gl.py` : `check_bench_kick` (avant / apres sur le meme corpus : -10 ms, F1 a -1 point au plus) et `FastAttack` seul. Pas encore fait de la spec : pas d'analyse a hop plus court, bloc de capture 256, WASAPI exclusif (a mesurer sur le portable de l'utilisateur). **Non verifie** : sur de vrais enregistrements et avec le micro reel.

**Synchro son / image, lot 3 (suite : bloc de capture de 256 ; issue #110 ; spec `docs/plans/2026-11-13-latence-bloc256-design.md`)** : le fil d'analyse traite chaque bloc recu, donc **le pas d'analyse est le bloc de capture** : `engine.audio.CAPTURE_BLOCK` = **512 par defaut** (10,7 ms a 48 kHz ; 256 = 5,3 ms seulement avec `CASUAL_AUDIO_BLOCK=256`), lu par `capture_block()`, utilise par la capture, le banc (`bench_kick.HOP`) et `mesure_latence.py`. Ce qui comptait en PAS compte en temps : le spectre de reference du classifieur kick / caisse claire est le plus recent qui a au moins `ATTACK_LOOKBACK_S` = 0,042 s (4 pas de 512, 8 de 256 ; `FeatureExtractor.ref_age`), historique garde `SPEC_KEEP_S` 0,1 s ; `STAMP_KEEP` 2048 blocs. **Repli automatique** : `SoundDeviceInput` date ses debordements (`OverflowCounter`) ; plus de `OVERFLOW_MAX` (5) en `OVERFLOW_WINDOW_S` (60 s) a 256 = `AudioController.check_block` (fil de garde d'une seconde) rouvre la meme entree a 512, une fois par session, sous un verrou partage avec `switch` et `refresh_devices` (qui gardent le bloc en cours) ; un enregistrement en cours s'arrete proprement, comme a tout changement d'entree ; repli impossible (entree debranchee) = message, l'entree de 256 reste ; message dans le statut et le journal. La part des basses et la brillance des phases (`core/phase.py`) sont lissees en temps (`SHARE_TAU_S`, `BRIGHT_TAU_S`). `capture_latency_ms` : la boucle de rendu lisait `latency_ms` comme une fonction (propriete) et l'avance automatique prenait 0 sans horodatage du pilote. **Mesure** (`mesure_latence.py`, 3 essais par taille) : total median 16,5-23,5 ms -> 9-16 ms, pire cas 31-35 -> 22-25 ms ; analyse mediane 9 -> ~1 ms. Banc (30 s) : datation -2 a -5 ms, kick sature F1 0,92 -> 0,97, rock F1 -1 point (un faux kick de plus, pendant l'apprentissage du classifieur, qui s'arme plus tot), claps sans kick moins de faux ; CPU de l'analyse 2,5 -> 4,9 % d'un coeur. **Suite non faite** : le « rendu » (kick -> premiere image) vaut souvent une image entiere en mediane (16 ms, jusqu'a 31) : la boucle de rendu lit peut-etre l'etat trop tot dans l'image (piste 5 de la spec). Hors perimetre : WASAPI exclusif. `check_gl.py` : `check_capture_block` (pur). **Non verifie** : la vraie carte son a 256 (debordements, crepitements) ; en WASAPI partage le pilote peut livrer deux blocs de 256 d'un coup toutes les ~10 ms : le pas serait alors toujours de 10,7 ms pour un CPU double (mesure en simulation seulement ; a relever : intervalle entre les callbacks sur la vraie carte).

**Piege : 256 par defaut cassait le son de l'enregistrement (14/11/2026, retour a 512)** : sur le poste de dev, carte son externe en WASAPI, les blocs de 256 se perdaient sous charge (interface gelee 300-900 ms) SANS que le pilote leve `input_overflow` : le repli a 512 ne partait jamais, l'enregistrement comblait chaque trou par du silence (crepitement ; 1221 trous, 54 s sur 124 s ; deja 307 trous / 11 s machine peu chargee ; la veille a 512 : 2 trous). Mesure : decodage de l'audio du .mp4 et compte des silences exacts de 2 ms et plus (la duree audio = la duree video : de vrais blocs perdus, pas un decalage d'horodatage). Depuis : 512 par defaut, 256 sur demande ; un bloc perdu se voit aussi au saut de l'horodatage (`block_gap` : plus de 2 blocs depuis le precedent), compte comme un debordement, pour que le repli marche meme sans drapeau du pilote. Gain de latence de 256 abandonne par defaut (~5 ms).

**Synchro son / image, lot 4 (pulsation et « Avance » ; issue #96)** : `core/pulse.py` (pur, temps injecte). `PulseClock` = boucle a verrouillage de phase calee sur les kicks REELS (naissance : un kick + un BPM fiable de `Rhythm` ; un kick a moins de 0,25 temps de la phase attendue la recale de 30 % et regle un peu la periode ; hors fenetre = ignore pour la phase ; un temps sans kick coute 0,06 de confiance, un kick bien place en rend 25 % de ce qui manque : de 1 a 0 en ~4 mesures sans kick ; le BPM du rythme regle doucement la periode, 3 desaccords de suite = changement de tempo, la periode saute). Etats `cale` (confiance >= 0,6) / `libre` / `perdue` / `absente`. `LeadGate` decide, pas par pas, si l'effet « sur kick » part : **predit** (instant `kick predit - avance`, l'avance etant plafonnee a 60 % de la periode) seulement si la pulsation est calee ET fiable (>= 75 % des derniers temps ont eu un kick : un breakbeat ou un kick un temps sur deux ne declenche jamais d'eclair sur un temps vide) ET `AudioAnalyzer` l'autorise (rythme `idle` et phase `groove` / `pic` : montee, cassure, drop restent reactifs) ; sinon a la **detection reelle**, comme avant. Un seul declenchement par kick : la detection reelle qui tombe dans [predit - 60 ms, predit + 100 ms] d'un declenchement deja parti n'en refait pas un ; un kick imprevu (contretemps) reagit tout de suite. **Branchement** (`AudioAnalyzer._lead_step`) : `self.beats`, `t_beat` (donc `beat`, `since_beat`) et les kicks des couches a sensibilite 1 (`edge_bg` / `edge_logo`) suivent le declenchement effectif ; `Rhythm`, `PhaseTracker` et la frappe aigue (charleys) gardent la detection reelle. Tout ce qui lit `beat` / `since_beat` / `beats` (onde de choc, aberration, pulsation du logo, strobe auto, foudre, VJ en rythme...) beneficie de l'avance sans changement. Reglage de salle `sync_lead_ms` (0..200 ms, defaut 0 = comportement d'avant ; PANIQUE le remet a 0 : a ressaisir ensuite), curseur « Avance » dans l'onglet *Affichage* (section « Synchro son / image ») et voyant (`explain.pulse_text`, « pulsation calee | avance 80 ms : effets en avance (ecart prediction - detection +3 ms) » ; `latest()["pulse"]`). **Sens de l'avance** : l'horloge est calee sur les instants de DETECTION ; l'effet part a (detection predite - avance), de sorte que la lumiere tombe sur le son si l'avance est le retard mesure par `tools/calibrer_avance.py` (lot 1). Granularite : un pas d'analyse (~10 ms). `check_gl.py` : `check_pulse` (dans `PURES` : horloge, manques, contretemps, perte, tempo, avance, double declenchement, garde-fous, branchement analyseur, voyant). **Non verifie** : avec une vraie calibration et le micro / projecteur reels (l'effet doit se voir en filmant : la lumiere au meme instant que le son) ; hors perimetre de ce lot : cycles lies au temps (fonte, cellules, respiration) en option de phase, bouton « Calibrer » dans la GUI (la calibration se lance avec `tools/calibrer_avance.py`).

**Synchro son / image, lot 5 (enveloppes continues, pulsation exposee, respiration ; issues #96, #97, #85)** :
- **8 enveloppes continues** (`engine.audio.BANDS8` : sub 20-60, grave 60-150, corps 150-400, bas-med 400-1000, med 1-2,5 k, presence 2,5-5 k, brillance 5-8 k, air 8-12 k ; auto-gain propre a chaque bande, attaque et relachement propres : relachement long aux graves (~230 ms), court aux aigus (~110 ms)) : `levels["bands"]` et `levels["band_rise"]` (derivee positive, unites d'enveloppe / s, plafonnee a 10). `levels` d'avant (3 bandes + rms) inchange. La derivee est publiee mais pas encore lue par un effet.
- **Nouvelles sources par couche** (menus « Le fond / Le logo reagit a », `core.audio_layers.SOURCES`, valeurs valides de `src_bg` / `src_logo`) : bandes fines `sub`, `corps` (150-1000 Hz), `presence` (1-5 kHz), `air` (5-12 kHz) = l'enveloppe continue de la bande (la plus forte de ses bandes), sans attaque ; grilles de pulsation `pouls` (chaque temps), `croches` (x2), `doubles` (x4), `mesure` (1 temps sur 4), `phrase8` / `phrase16` / `phrase32` (1 temps sur 8 / 16 / 32, #85) = enveloppe qui part sur l'evenement et decroit en 200 ms (`beat`, `since` : onde de choc, aberration, pulsation du logo ; `bass` = 0,8 x l'enveloppe : wobble). Les evenements viennent de `AudioAnalyzer._pulse_events` (`pulse_events` les compte) : franchissement de l'instant (temps predit - avance), donc **aussi en avance** ; « 1 temps sur N » compte depuis le « 1 » de la grille de l'operateur si elle existe (sinon depuis l'ancre de l'horloge) ; seulement quand la pulsation a une confiance >= 0,3 (`PULSE_USABLE`) : pulsation perdue = la couche se tait. `latest()["pulse_since"]` (temps depuis chaque evenement), `["pulse"]["phase_now"]` (phase a l'instant de la lecture), `["lead_s"]`. Le master de reactivite (et les phases) s'applique aux bandes et aux sources de pulsation (`state["react_m"]`). Pas de `has_kick` pour ces sources (damier au kick, derive des basses). Pas dans `AUTO_TABLE`.
- **Respiration sur la pulsation** (`breath_pulse`, reglage de salle 0..1, curseur « Resp. pulsation » de l'onglet *Auto* du panneau de controle, 0 par defaut, coupe par PANIQUE) : `core.pulse.swell` (cosinus : 1 sur le temps ENTENDU grace a l'avance, 0 a mi-chemin du suivant) ; la **presence de l'overlay** perd jusqu'a 50 % entre deux temps, la **luminosite du fond** jusqu'a 30 % quand les basses sont faibles, la **derive du fond** (`_bg_scroll`) varie de +-40 % avec la courbe. Sans pulsation calee ou libre, la courbe suit l'enveloppe des basses. Distincte de la respiration lente d'avant (`breath_overlay` / `breath_bg`, periode fixe), qui reste. `check_gl.py` : `check_bands_pulse` (dans `PURES`) et, dans `check_audio_layers` (pixels), sources de bande, de pulsation et respiration.
- **Non verifie** : a l'oeil et a l'oreille sur du vrai son (reglage de la profondeur de la respiration, de la decroissance de 200 ms des sources de pulsation).

**Synchro son / image, lot 6 (finitions)** :
- **Avance automatique** (remplace le bouton « Calibrer... » et sa fenetre, retires ; `tools/calibrer_avance.py` reste un outil de developpement) : `core/latency.py` (pur) estime l'avance en direct = **son** (retard de capture mesure, `audio_age_floor_ms` ; sans horodatage du pilote, `SoundDeviceInput.latency_ms`) + **detection** (`DETECT_MS` 15 ms, banc) + **image** (periode d'image MESUREE + temps GPU plafonne a une periode : le premier temps GPU, compilation comprise, depassait 500 ms) + **affichage** (`DISPLAY_MS` 25 ms, HYPOTHESE : projecteur), bornee 0..200 ms ; `LeadEstimator` lisse (2 s), arrondit a 5 ms, publie au plus une fois par seconde avec hysteresis de 4 ms. Reglages : `sync_lead_auto` (salle, **1 par defaut**), `sync_lead_est` (etat, ecrit par la boucle de rendu), `sync_lead_ms` (manuel). `effective_lead_ms(params)` est lue par l'analyse (avance des effets), le voyant de pulsation et l'enregistrement (`rec_delay_ms` moins l'avance). Onglet *Affichage* : radios Auto / Manuelle (curseur grise en Auto), ligne « Avance auto : 85 ms = son 22 + detection 15 + image 23 + affichage ~25 (suppose) » a hauteur fixe. La PANIQUE remet seulement l'avance manuelle a 0. `check_gl.py` : `check_lead_auto` (pur), `gui_lead_steps`. **Non verifie** : la justesse sur un vrai projecteur (l'hypothese d'affichage peut etre fausse de plusieurs dizaines de ms : mode manuel).
- **Cycles sur la pulsation** : `melt_beats` (look) et `breath_beats` (salle) = duree d'un cycle de la fonte / de la respiration lente en TEMPS (0 = `melt_period` / `breath_period` en secondes, comme avant ; sans pulsation calee ou libre : les secondes). `core.pulse.cycle_seconds`. Curseurs : « Cycle en temps » (onglet *Fonte du logo*) et « Temps » (onglet *Auto*). Le BPM change la vitesse, pas la phase : le cycle n'est pas cale sur un temps (a faire si la fonte doit demarrer sur le « 1 »). Cellules : `cell_speed` est une vitesse de derive, pas un cycle, donc non concernee.
- **Source `elan`** (montee du son) : la plus forte pente montante d'enveloppe parmi les 8 bandes (`band_rise` / `RISE_REF` 3, plafonnee a 1) pilote wobble et glitch ; sans attaque. La derivee des bandes est donc lue par un effet.
- **Menus de source** : une ligne de separation entre les familles (`audio_layers.SOURCE_GROUPS` : attaques, bandes fines + elan, grilles de pulsation). Si l'habillage (`skin`) gere mal les separateurs, le menu s'affiche sans.
- `check_gl.py` : `check_calibration` (conseil, plafond, commande), `check_bands_pulse` (elan, groupes, `cycle_seconds`), `gui_calib_steps` (fenetre, emission, analyse simulee, application).

Latence audio -> effet estimee : capture ~22 ms + detection ~25 ms + jusqu'a une frame
(16,7 ms) = ~45-65 ms, **au-dessus de la cible de 50 ms dans le pire cas**, et non mesuree
acoustiquement (impulsion sur le micro -> premiere image modifiee). Leviers : bloc de
capture de 256, fenetre d'analyse plus courte (au prix de la finesse des basses). Le visuel
de base garde en plus la latence propre d'`--averaging` (voir CLAUDE.md d'audio2wave).
Le generateur video `--synthetic` est limite par numpy a ~16 frames/s en 1080p : ce n'est pas
une mesure de l'application.
