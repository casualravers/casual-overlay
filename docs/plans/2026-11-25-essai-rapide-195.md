# Essayer une fonctionnalite plus vite : planche de preuves, fuzz des reglages, checklist d'essai (#195)

Spec issue du brainstorming de l'idee #195 « Quality improvement » (2026-11-25). Une seule PR : spec + code. Validation du design dans le chat.

## Contexte et decision

L'idee demandait une relecture globale du code. Etat des lieux (lecture seule) : 45 000 lignes, tres peu de code mort (4 candidats), architecture `core/ engine/ gui/` saine et testee ; les points chauds sont `tools/check_gl.py` (112 des 200 derniers commits), `gui/gl_gui.py` (`build_window` : 1 915 lignes) et `render.py`.

La douleur nommee par l'utilisateur n'est pas la qualite du code : c'est **le temps d'essai d'une nouvelle fonctionnalite**, qui s'allonge avec l'appli (reglages, cas limites, combinaisons). Un refactoring de la GUI ne le reduit pas (et c'est le chantier le plus risque du depot). On outille donc l'essai.

**Perimetre retenu** (3 pistes) : planche de preuves par PR, fuzz des reglages, checklist d'essai tiree de la spec.
**Hors perimetre, assume** : casser les fonctions geantes de la GUI, eclater `check_gl.py`, reequilibrer les groupes de la CI, mode demo `--demo`, regression visuelle par images de reference (les GPU different trop pour comparer des pixels). Ce sont des idees a reprendre a part si la douleur persiste.

## 1. Planche de preuves : `tools/planche.py`

- **But** : valider un rendu sur image, avant de lancer l'appli. Remplace « je lance et je tripote » par « je regarde une feuille de contact ».
- **Recette** : un fichier par fonctionnalite dans `tools/planches/<nom>.py`, qui expose `RECETTE` : un fond (neutre par defaut : degrade raye synthetique, sans ffmpeg ni micro), la source (texte ou image), des reglages de base, et une liste de **cas** `(etiquette, reglages a ajouter, instant en secondes)`. Un cas peut demander un zoom (zone + facteur).
- **Rendu** : le vrai `Renderer` sur un contexte autonome (comme `check_gl.py`), audio synthetique silencieux (`quiet`), logo pose avec `set_logo`. Si la recette a besoin d'un motif a calculer (tuile du texte), le cache disque est redirige vers un dossier temporaire (jamais le cache de l'utilisateur).
- **Sortie** : une planche PNG (une ligne par cas, etiquette = reglages ecrits sous l'image), plus les zooms demandes, dans `output/planches/<nom>.png` (dossier hors Git). `python tools/planche.py --liste` liste les recettes ; `python tools/planche.py texte-remplissage` en rend une ; `--sortie CHEMIN` change la destination.
- **Usage** : pour toute PR visuelle, la recette de la fonctionnalite est ajoutee a la PR et la planche est envoyee a l'utilisateur dans le chat **avant** de pousser. La premiere recette est `texte-remplissage` (reprend les scripts de #199 : vague, lettres transparentes / pleines, bordure ; la ligne du front, PR #211, y sera ajoutee a sa fusion).
- **Pas un test de pixels** : aucune image de reference, aucune comparaison. Un test verifie seulement que le generateur tourne sur une recette minimale et ecrit un PNG non vide.

## 2. Fuzz des reglages

### 2a. Partie pure : `core/fuzz.py` (stdlib, TDD)

- `draw_params(rng, keys=None, scopes=("look",)) -> dict` : tire un jeu de reglages valides **depuis `core.params_schema`** (plage `lo..hi` pour les nombres, `choices` pour les chaines, 0/1 pour les cases, longueur imposee pour les listes), en melangeant : valeurs au hasard, bornes exactes (`lo`, `hi`), defaut. Les bornes sont tirees plus souvent que le hasard pur (c'est la que ca casse).
- `cases(seed, n, ...) -> list[dict]` : `n` jeux reproductibles pour une graine. Meme graine = memes jeux, sur toute machine.
- `describe(case) -> str` : texte court des reglages differents du defaut, pour les messages d'echec.
- Aucune dependance au moteur, a numpy ni a GL (regle de `core/`, verifiee par `check_core_purity`).

### 2b. Partie rendu : `tools/fuzz_reglages.py` + verification dans la suite

- Pour chaque jeu : on le pose sur un `Renderer` (source Texte, puis source Image), on dessine quelques images (dont une apres 2 s simulees), et on echoue sur : **exception**, **erreur OpenGL** (`ctx.error`), **image impossible** (entierement noire alors que le logo est present et opaque, ou entierement uniforme). Le message donne **la graine, l'indice du cas et `describe(case)`** : rejouable avec `python tools/fuzz_reglages.py --graine G --cas 1 --depuis K` (**ecart a la spec initiale** : tout le prefixe 0..K est rendu, car l'etat du moteur passe d'un jeu au suivant et un cas seul ne se rejoue pas a l'identique).
- CI : `check_fuzz_reglages`, peu de cas (20) a graine fixe, dans le groupe « reste » (2 min), jamais dans « moteur » (14 min). Local : `--cas 500 --graine N`.
- **Premier perimetre** : reglages de portee `look` de l'overlay. Les transitions de scenes, le fond et l'audio viennent apres.

## 3. Checklist d'essai tiree de la spec

- Pas de nouvel outil : une **convention**. Quand je pousse une PR, son corps contient deux listes tirees de « Comment je saurai que c'est bon » de l'issue : **« Verifie par Claude »** (chaque ligne cite le test ou la planche qui le prouve) et **« A verifier par toi »** (oeil, projecteur, micro, telephone).
- Modifications : gabarit `.github/pull_request_template.md` (la section « A tester en vrai » devient les deux listes) et une ligne dans `CLAUDE.md` (limite de 300 lignes a respecter : on remplace, on n'ajoute pas).

## Verifications (dans `tools/check_gl.py`)

- `check_fuzz` (**pure**, dans `SUITE` et `PURES`) : meme graine = memes jeux ; tous les jeux passent `coerce_params` sans correction ; les bornes sont tirees ; `describe` ne cite que ce qui change ; `core/fuzz.py` est pur (couvert par `check_core_purity`).
- `check_fuzz_reglages` (**rendu**, dans `SUITE` seulement) : le fuzz tourne sur 20 jeux a graine fixe sans echec ; un echec injecte (jeu qui provoque une exception simulee) est bien rapporte avec sa graine.
- `check_planche` (**rendu**, `SUITE` seulement) : recette minimale -> PNG non vide, etiquettes presentes ; `--liste` trouve `texte-remplissage`.

## Risques

- **Fuzz instable en CI** (llvmpipe plus strict que le GPU de l'utilisateur) : un echec en CI doit etre rejouable avec sa graine ; si un cas s'avere un faux positif, on durcit le critere « image impossible » plutot que de retirer le test.
- **Fuzz trop lent** : 20 jeux a graine fixe en CI ; la duree est mesuree et restee sous ~60 s, sinon on reduit.
- **Planche qui derive de l'appli** (recette copiee du moteur) : elle utilise les memes `Renderer` et reglages, jamais une copie de leur logique.

## Non verifie (demande le materiel)

- Que la planche suffit a l'utilisateur pour valider sans lancer l'appli (a juger sur les premieres PR).
- Aucun test de pixels sur projecteur ni de rythme : ils restent manuels.

## Ecarts constates a la realisation

- Recette initiale `texte-remplissage` au lieu de `texte-front` (la ligne du front est dans la PR #211, pas encore fusionnee).
- `Cas` et `Recette` vivent dans `tools/planches/__init__.py` (importables par les recettes sans cycle).
- Fuzz rendu : un cas sur deux epingle la presence du logo (opacite 1, tailles 0,5, fonte a 0) ; le tirage cachait le logo dans presque tous les jeux. La fonte profonde est un cacheur legitime. `--depuis K` rejoue le prefixe. Balayages 300 x 2 graines et 1 500 jeux : aucun echec (pas de bug reel sur la portee `look`).
